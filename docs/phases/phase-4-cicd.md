# Phase 4 — CI/CD with Azure DevOps

**Status:** Completed (with documented execution limitation)
**Duration:** Multi-iteration (pipeline design, service connection troubleshooting, scope adjustment)
**Dependencies:** Phase 3 (Data Pipeline)

---

## Objective

Automate the validation, testing, and deployment of the project using Azure DevOps. This phase establishes:

- A secure authentication mechanism between Azure DevOps and Azure (no stored secrets)
- Reusable YAML templates for Terraform and Python workflows
- Pipelines that validate, test, and deploy under manual approval
- Branch policies and governance rules
- A foundation that can be activated on any Azure DevOps organization with billing configured

---

## Context

### Why CI/CD

Manual execution of validation and deployment has three problems:

1. **Inconsistency:** different developers may run different commands
2. **No audit trail:** there is no automatic record of who changed what and when
3. **Human error:** `terraform apply` executed without a plan review can cause unintended changes

CI/CD solves these by making the pipeline the single source of truth for validation and deployment.

### Why Azure DevOps

Azure DevOps was chosen because:

- It is one of the technologies explicitly required by the project scope
- It has native integration with Azure (Service Connections, Workload Identity)
- It supports free private repositories and pipelines
- It is widely used in Brazilian enterprises, where the professional objective is focused

### Architectural Decisions

Three decisions shaped the design:

| Decision | Choice | Rationale |
|----------|--------|-----------|
| Authentication | Workload Identity Federation (OIDC) | No secrets, tokens issued per run, modern best practice |
| Pipeline structure | Main pipelines + reusable templates | Reduces duplication, easy to extend |
| Apply approval | Manual via Azure DevOps Environment | Governance: no change reaches Azure without human review |

## Implementation

### 1. Azure DevOps Organization and Project

- **Organization:** `jc-carvalho-org`
- **Project:** `jc-azure-sre-databricks-platform`
- **Visibility:** Private
- **Repository:** GitHub (existing repo connected via GitHub App)
- **Variable group:** `jc-azure-sre-common`

The variable group holds non-secret values used across pipelines:

| Variable | Purpose |
|----------|---------|
| `AZURE_SUBSCRIPTION_ID` | Subscription ID |
| `AZURE_LOCATION` | Default region (`brazilsouth`) |
| `RESOURCE_GROUP_NAME` | Target Resource Group |
| `TF_STATE_RG` / `TF_STATE_SA` / `TF_STATE_CONTAINER` | Terraform backend config |
| `TF_STATE_KEY` | State file name for `dev` |
| `TERRAFORM_VERSION` | Pinned Terraform version |
| `PYTHON_VERSION` | Pinned Python version |

### 2. Service Connection with Workload Identity Federation

A Service Connection named `azure-jc-carvalho` was created using **Workload Identity Federation (manual)**. This is the modern approach that eliminates the need to store any secret in Azure DevOps.

Components:

| Component | Value |
|-----------|-------|
| App Registration | `jc-sre-databricks-pipeline` |
| Service Principal | created automatically with the App Registration |
| Federated Credential | name `azure-devops-federated` |
| Issuer | `https://login.microsoftonline.com/<tenant-id>/v2.0` |
| Subject | generated by Azure DevOps for the specific service connection |
| RBAC role | Contributor (scope: subscription) |

**Note on the issuer format:** Azure DevOps recently migrated from the legacy issuer (`https://vstoken.dev.azure.com/<org-id>`) to the Microsoft Entra issuer (`https://login.microsoftonline.com/<tenant-id>/v2.0`). The initial configuration using the legacy issuer failed with `AADSTS700211`. The final configuration uses the Entra issuer, and the exact subject was copied from the Azure DevOps UI.

**Note on RBAC scope:** the Contributor role was assigned at the **subscription** scope, not at the Resource Group scope, because the project lifecycle includes periodic `terraform destroy` and recreate cycles. Assigning at the subscription level allows the pipeline to create the Resource Group itself. This is documented as an intentional trade-off: broader scope in exchange for a self-contained pipeline.

### 3. Reusable Templates

Six templates were created under `azure-devops/templates/`:

| Template | Purpose |
|----------|---------|
| `variables.yml` | Common variables (versions, paths, backend config) |
| `terraform-validate.yml` | `fmt -check`, `init`, `validate` |
| `terraform-plan.yml` | `init`, `plan`, publish plan artifact |
| `terraform-apply.yml` | Download plan artifact, `apply` |
| `python-lint.yml` | `ruff check`, `ruff format --check` |
| `python-test.yml` | Install deps, `pytest` with coverage, publish results |

Each template declares its own parameters with sensible defaults, allowing the pipeline to override when needed.

### 4. Main Pipelines

Two main pipelines orchestrate the templates:

**`azure-devops/pipelines/terraform-pipeline.yml`**

Stages:

1. **Validate** — `fmt`, `init`, `validate`
2. **Plan** — `init`, `plan`, publish `tfplan` and `tfplan.txt` artifacts
3. **Apply** — download artifact, `apply` (runs only on `main` and `develop`, requires manual approval)

The `Apply` stage uses a `deployment` job referencing an Azure DevOps Environment (`jc-azure-sre-databricks`). The Environment is configured with an approval check, so the apply is paused until a designated approver reviews and approves.

**`azure-devops/pipelines/python-pipeline.yml`**

Stages:

1. **Lint** — `ruff check`, `ruff format --check`
2. **Test** — `pytest` with coverage, publishes test results and code coverage

The Python pipeline is fully independent of Azure resources: it runs entirely on the hosted agent.

### 5. Trigger and Path Filters

Both pipelines use path filters to avoid unnecessary runs:

- Terraform pipeline runs only when `terraform/**` or `azure-devops/**` changes
- Python pipeline runs only when `python/**` or `azure-devops/**` changes

This reduces the consumption of hosted pipeline minutes and provides faster feedback.

## Execution Limitation

### The problem

The pipelines could not be executed on Microsoft-hosted agents. The error was:

```
##[error]No hosted parallelism has been purchased or granted.
Please set up billing or purchase parallel jobs.
```

### Root cause

Since 2024, Azure DevOps organizations created without prior billing history do not automatically receive the free Microsoft-hosted parallel job. To obtain it, the organization must either:

1. Set up billing by linking a valid Azure subscription, OR
2. Purchase parallel jobs

### Why linking billing was not possible

The project runs on an **Azure for Students** subscription. When attempting to link it for billing, Azure DevOps returns:

> This subscription cannot be used for purchases.

Azure for Students (like Free Trial and most promotional offers) is not an eligible payment method for Azure DevOps billing. Only Pay-As-You-Go, Enterprise Agreement, and CSP subscriptions are accepted.

### Alternatives considered and rejected

| Alternative | Why rejected |
|-------------|--------------|
| Self-hosted agent | Makes the repository dependent on a specific personal machine; fragile; introduces ambiguity about the project's reproducibility |
| Upgrade to Pay-As-You-Go | Not appropriate for a portfolio project with a fixed budget; the value is not worth the cost at this stage |
| GitHub Actions instead of Azure DevOps | Would abandon a project requirement and remove the opportunity to demonstrate Azure DevOps knowledge |
| Wait for future eligibility | Not viable as a plan; unpredictable timing |

### Decision

The pipelines are **implemented, versioned, and ready to run**. They are not executed in the current organization due to the subscription limitation. The same validation they perform is available locally via `make` targets, which are documented in the README and used routinely.

This is documented as a deliberate architectural choice in **ADR-002**, which will be added in a future phase to preserve the reasoning while keeping the ADR log organized.

### What this means in practice

| Context | Behavior |
|---------|----------|
| Azure DevOps with Pay-As-You-Go subscription | Pipelines run automatically on push and PR |
| Azure DevOps with Azure for Students | Pipelines cannot run; local `make` targets are used |
| Local development | `make validate`, `make lint`, `make pipeline-test` replicate the pipeline behavior |

## Validation

### Local equivalent of the pipeline

The pipelines were validated locally by reproducing their steps:

```bash
# Equivalent to python-pipeline.yml (Lint stage)
cd python
source .venv/bin/activate
ruff check src/ tests/
ruff format --check src/ tests/

# Equivalent to python-pipeline.yml (Test stage)
pytest tests/ \
  --junitxml=test-results.xml \
  --cov=src \
  --cov-report=xml:coverage.xml \
  --cov-report=term-missing \
  --cov-fail-under=35

# Equivalent to terraform-pipeline.yml (Validate stage)
cd terraform/environments/dev
terraform fmt -check -recursive
terraform init -backend=false -input=false
terraform validate
```

**Results:**

| Check | Result |
|-------|--------|
| `ruff check` | All checks passed |
| `ruff format --check` | All files formatted |
| `pytest` | 10 passed, coverage 35.71% |
| `terraform fmt -check` | No changes needed |
| `terraform validate` | Success! The configuration is valid |

### YAML syntax validation

All 13 YAML files were validated for correct syntax using Python's `yaml.safe_load`.

## Lessons Learned

### What worked well

- **Workload Identity Federation** eliminated the need for secrets from the start. The only friction was the issuer format change (documented above), which was resolved by using the exact values Azure DevOps generated.
- **Templates** made each pipeline file concise and readable. The main pipeline files focus on structure; the details live in reusable templates.
- **Path filters** prevent unnecessary pipeline runs. A Python-only change does not trigger the Terraform pipeline and vice versa.
- **Coverage baseline** was set to the current real value (35%) instead of an aspirational number. This is honest and prevents false failures while signaling room for growth.

### Adjustments made

1. **Issuer format migration.** Azure DevOps moved from the legacy issuer to the Microsoft Entra issuer. Documentation in the project was updated to reflect the correct configuration.

2. **RBAC scope.** The initial plan was to assign Contributor at the Resource Group scope. This was changed to the subscription scope to allow the pipeline to create the Resource Group itself. Trade-off documented.

3. **Coverage threshold.** Initial value was 70%, which the project does not meet. It was set to 35% (the current baseline) with a comment explaining the intent to raise it as tests are added.

4. **Terraform formatting.** The initial `terraform fmt -check` found formatting drift in `backend.tf` and `provider.tf`. Applied `terraform fmt -recursive` to fix.

### What would be done differently

- **Verify subscription eligibility before designing the pipeline.** The billing limitation was discovered after the pipelines were built. In a corporate environment, checking subscription eligibility would be the first step.
- **Test the Workload Identity flow with a minimal pipeline before building complex templates.** This isolates authentication issues from pipeline issues.
